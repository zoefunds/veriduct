# VERIDUCT

**Authenticated observations. Independent adjudication. Bounded operations.**

VERIDUCT is a public Studionet demonstration of a GenLayer service-reliability covenant network. A service owner publishes an immutable reliability policy, separately owned publisher identities anchor the SHA-256 digest of exact HTTPS response bytes, and GenLayer validators independently retrieve and interpret those bytes. A proven breach can create only the remedy envelope the covenant authorized, and that envelope affects the deployed ServiceControl demonstration adapter only after two finality-gated child transactions.

> **Evidence disclosure:** the bundled provider and corroborator feeds are deterministic demonstration fixtures generated by the same `veri-duct.vercel.app` deployment. Their different wallet owners prove distinct onchain publisher identities, not independent monitoring infrastructure or independently acquired telemetry. Exact-byte authentication proves which bytes validators fetched; it does not prove that the values are accurate real-world measurements. No external payments service is connected to ServiceControl.

## Why GenLayer

Ordinary deterministic contracts can compare a number with a threshold, but the production decision here requires validators to determine whether heterogeneous provider and monitor reports describe the same service window, satisfy the natural-language covenant clauses, materially corroborate one another, and justify the requested operational response. VERIDUCT confines nondeterminism to that semantic comparison. Publisher ownership, hostname binding, HTTPS status, exact-byte digest matching, freshness, distinct-owner quorum, covenant version, adapter compatibility, remedy limits, expiry, action digest, finality, and replay protection remain deterministic.

## Security properties

- A source counts only when its registered wallet, exact canonical hostname, URL, observation time, validity window, HTTP success status, and fetched SHA-256 digest match its immutable anchor.
- Publisher keys and their onchain owners must both be distinct to satisfy quorum.
- Covenant versions are immutable, owner-locked, delayed, and monotonic; every case freezes the active covenant digest.
- A covenant owner must equal target governance, preventing a new attacker-owned service key from taking control of an existing target.
- The router has no hard-coded target method or action class. Governance registers `(action_id, target, payload_schema_digest)` only after the target attests the same governance and schema support.
- Case, covenant, verdict, holder, issue time, expiry, and TTL are frozen in the mandate record. Target, action, intensity, canonical payload bytes, payload schema, case, and covenant form the recomputed execution digest; holder and expiry are enforced separately.
- Adjudication-to-issuance and dispatch-to-application are separate `FINALIZED` child transactions; `ACCEPTED` parent state grants no authority.
- The target independently verifies the router and governance, stores the applied digest, treats identical delivery idempotently, and rejects conflicting replay.
- Fetch failure, stale data, oversized responses, digest mismatch, origin substitution, duplicate publishers, semantic conflict, or insufficient corroboration fails closed.

## Application and backend

The Next.js 16 application deploys the interface and evidence Route Handlers together on Vercel. There is no privileged backend signer, database, indexer, or offchain authority service. The public demonstration endpoints are:

- `GET /api/evidence/provider/[at]` — provider reliability report for an explicit Unix observation time
- `GET /api/evidence/monitor/[at]` — separately shaped corroborator fixture for the same explicit observation time
- `GET /api/provenance` — machine-readable operator, collection-method, and independence disclosure
- `GET /api/build` — deployed frontend Git commit and runtime deployment identity

Both routes return deterministic JSON for a valid timestamp and HTTP 400 for invalid input. The browser hashes the received bytes before filling an anchor transaction. Onchain reads use `LATEST_FINAL`; wallet-signed writes wait for `FINALIZED` before the interface reports success.

## One-click production test autofill

Every write surface includes a **Demo autofill** control containing complete synthetic test data rather than empty examples. Evidence autofill requests a fresh provider or corroborator fixture, computes the real SHA-256 digest in the browser, and fills the exact publisher key, URL, observation time, validity, and digest. Submitted snapshot keys are retained locally for the next form, while case creation still loads and validates their finalized onchain records. Case autofill reads the currently active covenant and constructs a 20-minute, intensity-60 ServiceControl request inside the policy's 30-minute TTL. Adjudication, mandate dispatch, and reconciliation reuse the exact submitted case and payload values; each contract independently requires the corresponding finalized onchain record and exact action digest. Every write still requires the user's wallet approval and the correct owning account.

## Local verification

Requirements: Node.js 20 or newer and Python 3.12 or newer.

```bash
npm install
npm run typecheck
npm test
npm run test:contracts
npm run build
```

The current verification baseline is 26 passing Python tests, five parsed and validated Intelligent Contract sources, a passing TypeScript check, and a successful production build. The model suite covers the full registry-to-target path and explicit regressions for target seizure, forged publisher ownership, origin substitution, fake quorum, every material envelope-field mutation, non-proven issuance, and replay after application. The `/verification` interface re-fetches both frozen bodies and reads the active covenant, adjudicated case, applied mandate, and ServiceControl receipt at `LATEST_FINAL`.

## Reproduce the deployment proof

Run `npm run verify:deployment`. The verifier downloads every deployment transaction from Studionet, decodes its `contract_code`, byte-compares it with the corresponding file in `contracts/`, confirms every listed workflow transaction is `FINALIZED`, distinguishes successful GenVM execution from expected GenVM rejection, re-hashes both frozen HTTPS bodies, and reads the covenant, case, mandate, and ServiceControl receipt directly at latest-final state. `npm run verify:deployment:report` writes the complete machine-readable result to [verification-report.json](./verification-report.json). The committed report identifies the same Git commit from both the verifier checkout and the live `/api/build` endpoint.

This check requires network access to the public RPC and application. It never requires a wallet or private key.

## Deployment

The repository pins `genlayer@0.39.1` and deploys only to stable Studionet:

```bash
npm install
npx --no-install genlayer deploy
cp .env.generated .env.local
npm run build
```

Deployment order is PublisherLedger → CovenantBook → MandateRouter → Adjudicator → one-time adjudicator binding → ServiceControl → adapter registrations. Every write must finalize before the dependent step begins. `deploy/deployScript.ts` writes local generated configuration; the reviewed production source of truth is [deployment-manifest.public.json](./deployment-manifest.public.json).
